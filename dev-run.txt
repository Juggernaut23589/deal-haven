  !!! CRITICAL — UPSTASH TLS FIX !!!
  ------------------------------------
  The ioredis client in backend/src/config/redis.ts uses plain TCP by default.
  Upstash REQUIRES TLS on port 6380. If you use Upstash you MUST add a `tls`
  option to the Redis constructor in that file, otherwise connections will hang
  and the server will fail to start. Add this to the ioredis options object:

    tls: { rejectUnauthorized: false }

  If you use local Redis (port 6379), TLS is NOT needed — leave it as-is.

================================================================================
  SECTION E — KNOWN ISSUES & FIXES
================================================================================

  ISSUE 1 — Upstash Redis / TLS connection hang
  -----------------------------------------------
  Symptom:  Server starts then hangs or Redis shows "ECONNREFUSED" or times out
            after several retries on port 6380.
  Root cause: backend/src/config/redis.ts creates an ioredis client without TLS
              options. Upstash mandates TLS on port 6380.
  Fix:      In backend/src/config/redis.ts, add `tls: {}` to the Redis options:

    redisClient = new Redis({
      host: process.env.REDIS_HOST ?? 'localhost',
      port: parseInt(process.env.REDIS_PORT ?? '6379', 10),
      password: process.env.REDIS_PASSWORD,
      db: parseInt(process.env.REDIS_DB ?? '0', 10),
      tls: process.env.REDIS_PORT === '6380' ? { rejectUnauthorized: false } : undefined,
      // ... rest of options
    });

  ISSUE 2 — PM2 using `npm run dev` in production
  -------------------------------------------------
  Symptom:  dev-setup.txt Step 6A says:
              pm2 start npm --name "ashimarket-api" -- run dev
            This starts tsx watch which is a dev-only tool. It works but is
            wasteful (tsx compiles on each change) and not suitable for prod.
  Fix:      Always use the compiled production build for PM2 in production:
              npm run build                 # compile first
              pm2 start npm --name "ashimarket-api" -- run start
            The `start` script runs `node dist/index.js` — no compilation at
            runtime, much faster and more stable.

  ISSUE 3 — `sharp` native binary on ARM (Oracle Ampere A1)
  -----------------------------------------------------------
  Symptom:  `npm install` completes but the server crashes on image upload with
            "Error: Could not load the "sharp" module using the linux-arm64 runtime"
  Fix:      On the Oracle ARM VM, run:
              npm uninstall sharp
              npm install --cpu=wasm32 sharp
            Or use the generic ARM-compatible build:
              npm install --ignore-scripts=false sharp
            Then re-run: npm run build && pm2 restart ashimarket-api

  ISSUE 4 — Supabase paused database
  ------------------------------------
  Symptom:  Backend starts but all DB operations fail with "connection refused"
            or "ECONNREFUSED" against db.XXXX.supabase.co.
  Fix:      Log into https://supabase.com → select your project → click
            "Restore project". Wait ~60 seconds, then:
              pm2 restart ashimarket-api

  ISSUE 5 — Frontend build fails with missing env vars
  -----------------------------------------------------
  Symptom:  `npm run build` outputs warnings about undefined NEXT_PUBLIC_ vars
            or the built app cannot reach the API.
  Fix:      Ensure ~/ashimarket/frontend/.env.local exists with all 3 vars:
              NEXT_PUBLIC_API_URL=http://YOUR_ORACLE_IP:4000/api/v1
              NEXT_PUBLIC_SOCKET_URL=http://YOUR_ORACLE_IP:4000
              NEXT_PUBLIC_APP_URL=http://YOUR_ORACLE_IP:3000
            Then re-run: npm run build && pm2 restart ashimarket-web

  ISSUE 6 — Port 3000 / 4000 not reachable from browser
  -------------------------------------------------------
  Oracle Cloud has TWO independent firewall layers — BOTH must allow the port:
    Layer 1 — VCN Security List (Oracle console):
              Hamburger → Networking → Virtual Cloud Networks → your VCN
              → Security Lists → Add Ingress Rule for TCP 3000 and 4000
    Layer 2 — Ubuntu iptables (inside the VM):
              sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 3000 -j ACCEPT
              sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 4000 -j ACCEPT
              sudo netfilter-persistent save
  Verify which rules are active:
    sudo iptables -L INPUT -n --line-numbers

  ISSUE 7 — BullMQ / background jobs fail to start
  --------------------------------------------------
  Symptom:  Server starts but logs show BullMQ errors about missing Redis
            connection or "maxRetriesPerRequest must be null for blocking commands".
  Fix:      BullMQ requires a SEPARATE ioredis connection with
            `maxRetriesPerRequest: null`. This is distinct from the cache client.
            In backend/src/jobs/notification.job.ts, ensure the Queue and Worker
            are created with a connection config of `maxRetriesPerRequest: null`.

  ISSUE 8 — Prisma migration fails: "Table already exists"
  ---------------------------------------------------------
  Symptom:  `npx prisma migrate deploy` fails with PG error about duplicate
            table or constraint already existing.
  Fix:      The database already has some schema applied (e.g. from an earlier
            db:push). To resolve cleanly for dev:
              npx prisma migrate reset --force    # WIPES DATA — dev only
              npm run db:seed
            For production: manually baseline the existing schema:
              npx prisma migrate resolve --applied "migration_name"

  ISSUE 9 — TypeScript build errors on noUnusedLocals / noUnusedParameters
  --------------------------------------------------------------------------
  Symptom:  `npm run build` fails with TS errors about unused variables.
  Fix:      The tsconfig.json has strict unused-variable checks enabled. Before
            building for production, run:
              npm run typecheck
            Fix all reported errors. Do NOT disable strict mode.

  ISSUE 10 — Seed script fails with "P2002 Unique constraint failed"
  ------------------------------------------------------------------
  Symptom:  `npm run db:seed` errors because demo users/listings already exist.
  Fix:      The seed script should be idempotent (using upsert). If it is not,
            clear the database first:
              npx prisma migrate reset --force    # dev only — wipes all data
              npm run db:seed
